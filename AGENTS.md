# AGENTS.md

Personal dotfiles applied with mise: `mise bootstrap`, `[dotfiles]`, `[tools]`, and tasks. Omarchy and macOS are the only supported profiles.

This file holds the rules, not an inventory. The config is the source of truth for what is managed, and README.md for commands and user-facing behavior; read them instead of copying details here.

## Shape
- `bin/dotfiles` is the curl entrypoint and daily wrapper: it prepares git, mise and the checkout, links `modules/` as mise `conf.d`, records the machine's profile and purpose, then runs `mise bootstrap`.
- The wrapper evaluates from HOME unless given an explicit context, and an explicit context applies to every step; never mix the two.
- `modules/<name>/` is one conf.d folder: env files, config sources, an optional `bootstrap.sh`, and `tests/`. An app with config or steps gets its own module; pure installs and dev runtimes go in the shared package and devtools modules.
- Env files layer shared → platform → OS/session, and the most specific wins. A profile describes the OS and session, never the hardware.
- Purpose (work or personal) is independent of profile and lives in a local, untracked marker. Changing it only updates the marker and discovery settings; it never provisions.
- README images are generated by `.github/assets/render/render.py`; re-render when the wrapper's UI changes.

## Rules
- Who writes a file decides how it deploys: link what only the repo writes; merge or edit just the owned keys of files the app also writes; copy only when a link cannot work, with the reason beside the entry.
- Always give an explicit relative `source`.
- Changing a directory's link mode: remove the old link on each machine first, or mise writes through it into the repo.
- Declare packages with the platform's native manager, in the most specific env file that needs them. Purpose restrictions use mise's native package `env` option; no parallel policy engine.
- One failed package install stops the run, so anything optional that can fail belongs in a fail-soft task instead.
- Imperative steps are idempotent `bootstrap:<module>` tasks that fail soft: say what was skipped and exit 0. Only steps whose failure must stop the run, such as privilege policy or compositor config validation, exit non-zero.
- Files the wrapper generates belong to the wrapper; never hand-edit them.
- No secrets in the repo or in linked files: the repo is public. 1Password is reached only through the secrets module.
- Privilege changes are validated before install and target the real invoking user. Never weaken that to get a step through.
- Shared user configs such as Git: own one bounded block, publish the new owner before removing the old one, and preserve everything else.
- Retiring something: drop the declaration and document manual cleanup. Unconditional removal (`mode = "absent"`) only when intended and approved.
- Use apps' standard config locations; don't add a second deployer to fake what mise does not support.
- Tests execute shipped code and live beside it. No tests that grep config text, and no per-module READMEs.
- mise bootstrap is new: read <https://mise.jdx.dev/bootstrap.html> and <https://mise.jdx.dev/dotfiles.html> instead of guessing syntax.

## Platform boundaries
- Omarchy owns its system tree, its Hyprland entry point, its desktop and gaming stack, and the configs and tools its installers manage. Hook in through its extension points, set only the keys we own in configs it ships, and don't redeclare tools it already installs.

## Verify before reporting done
- Use the README's preview and validation commands, run from HOME. Experiment in isolated HOME/XDG/mise directories; a preview must not change live state.
- Fix test fixtures, not production safety guards.
- A dry run or a macOS-hosted check is not proof for native Linux; check the affected OS directly.
- Apply live only when authorized, then require a clean status and a no-change repeat.
